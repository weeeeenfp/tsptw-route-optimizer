# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TSPTW route optimization system (國立勤益科技大學資工系實務專題): solves single-vehicle delivery/pickup routing with time windows. Reads delivery locations + time windows from Excel/JSON, gets travel times from Google Maps Distance Matrix API, solves with OR-Tools or a DP engine, and returns route order, ETAs, lateness, and Google Maps navigation URLs.

**Before doing any work in this repo, invoke the `capstone-project-workflow` skill.** It defines the mandatory dev workflow (sync repo → read contracts → make change → verify by actually running it → update CHANGELOG → never self-merge PRs) and the four submission-document formats. This CLAUDE.md covers architecture/commands only — the skill covers process.

## Commands

```bash
# install deps
pip install -r requirements.txt

# run all tests (stdlib unittest, no pytest)
python -m unittest discover -s tests

# run a single test file / case
python -m unittest tests.test_input_validation
python -m unittest tests.test_input_validation.TestClassName.test_method_name

# run one optimization locally (no API), per config.json
python scripts/run_routing.py

# start the API (Render runs this exact command — do not change the module:app path)
uvicorn API_main:app --host 127.0.0.1 --port 8000
# docs at http://127.0.0.1:8000/docs

# start the static frontend (must use 5173 — it's in the backend's CORS allowlist)
python -m http.server 5173
# or double-click start-frontend.bat on Windows
# open http://127.0.0.1:5173/ (landing) or /app.html (main app)
# NEVER open the HTML via file:// — origin becomes null and CORS blocks all fetches

# compare OR-Tools search strategies
python scripts/compare_ortools_strategies.py

# lint (no config file present, run ad hoc)
ruff check .
```

There is no build step for the frontend (plain HTML/CSS/JS, no bundler). After editing `app.js`/`style.css`, hard-refresh (Ctrl+F5) or bump the `?v=` query param in `app.html` — the browser aggressively caches these.

## Architecture

### Backend pipeline (single request-response flow, no persistence layer)

```
config.json  (+ config.local.json, then an API-key env var, each overriding the last)
    ↓
core/app_config.py         — load config, merge with per-request payload
    ↓
core/input_validator.py    — validate types, bounds, time formats, Google Maps limits
    ↓
core/route_service.py      — orchestrator: delayed/cancelled/skipped filtering, priority, start/end selection
    ↓
core/google_maps_api.py    — Distance Matrix calls + matrix_cache.json (chunked, superset-slicing cache)
    ↓
core/route_service.py      — pick solver
    ↓
core/or_tools_engine.py  or  core/dp_engine.py   — solve
    ↓
core/route_service.py      — assemble route_details, lateness, navigation URLs
    ↓
scripts/run_routing.py (writes output_result_file)  or  API_main.py (returns JSON)
```

Entry points: `API_main.py` (FastAPI, `POST /api/v1/optimize-route`, `POST /api/v1/validate-address`, `GET /api/v1/health`) and `scripts/run_routing.py` (CLI, one-shot, no server). Both funnel into the same `core/route_service.py`.

**Everything backend-internal imports as `from core.xxx import ...`.** `scripts/` CLIs add the project root to `sys.path` themselves, but relative paths (config files, caches) are resolved from the working directory — always run from the repo root.

### The one contract you must not violate

`route_indices`, `depot_index`, `start_index`, `end_index`, `current_index`, `completed_indices`, etc. are all **array indices into the `locations` list as submitted**, never database IDs. Frontend and backend both key off array position, not `location.id`. Don't mix these up when touching request/response handling on either side — see `LLM_COLLABORATION_GUIDE.md` rule 4-5 for the full rationale.

### In-transit re-optimization

The frontend always sends the *complete* `locations` array (original order preserved) plus `current_index`/`current_time_seconds` and per-location `status` (`completed`/`cancelled`/`skipped`/`delayed` + `rescheduled_time_window`). The backend excludes finished/cancelled/skipped stops and re-solves from `current_index`, but still returns indices against the original array — see `reoptimization` in the response and `route_details[].active_index` for debugging. This mechanism (not a separate endpoint) is how "customer not home", "reorder", and "mark delivered" all work.

### Frontend (`index.html`, `app.html`, `app.js`, `style.css`, no framework/build)

- `index.html` — marketing landing page (deliberately reveals no real place names; OSM route animation is generated by `scripts/build_landing_map.py` into a marked block — don't hand-edit that block).
- `app.html` — app shell: header (API base / role toggle / connection light), 3 tabs (upload / route+loading / delivery-or-pickup management).
- `app.js` — all logic lives here: state (`S` object), Excel parsing/column mapping, API calls, rendering, ETA math, exception re-planning, manual reorder, role toggle. See `FRONTEND_GUIDE.md` §9 for a function-by-feature lookup table.
- Role toggle (`toggleRole()`) shows/hides `.admin-only` elements but always keeps the connection-status dot visible.
- Must be served from an allowlisted CORS origin (`127.0.0.1:5173` by default, matching `config.json`'s `api_server.cors_allow_origins`) — opening via `file://` breaks all API calls.
- `FRONTEND_GUIDE.md` is the authoritative frontend doc — read it before touching `app.js`.

### Config and secrets

`config.json` is checked in and must never contain a real API key. Key resolution order: `config.json` → `config.local.json` (gitignored, same shape, only override the fields you need) → the first env var in `core.app_config.API_KEY_ENV_VARS` that has a non-empty value — `ROUTING_API_KEY_0814` (what Render is set to since the 2026-08-14 key rotation), then `ROUTING_API_KEY`, then `GOOGLE_MAPS_API_KEY`. Each step overrides the previous. The "non-empty" check matters: Render makes it easy to save a variable as an empty string, and that must fall through to the next name rather than count as "set".

### Tests

`tests/` uses stdlib `unittest` only (no pytest, no extra framework). Each file targets one concern: input validation bounds, config merge/override precedence, matrix cache slicing, priority preferences, manual route ordering, departure time, address validation. `test_cases/` holds larger fixture-driven scenario scripts (Excel generation, screenshot capture, report workbook builds) used for the capstone's report deliverables — those are not part of `python -m unittest discover`.
